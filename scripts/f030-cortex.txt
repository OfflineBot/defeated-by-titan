# F-030 — the cut: a blade swept along one tick of the player's fall crosses the amber cortex
# on the husk's nape, and the husk dies.
#
# cargo run -- --offscreen --script scripts/f030-cortex.txt --ticks 158 \
#              --screenshot docs/images/f030-cortex.png
#
# and, as a SEPARATE run, the one that returns a usable exit code:
#
#   cargo run -q -- --headless --script scripts/f030-cortex.txt --ticks 700
#
# ⚠️ **A `--screenshot` run is not a verdict.** `debug::screenshot::exit_when_written` owns the
# ending and writes `AppExit::Success` the moment the PNG is on disk, without ever reading
# `run.failures` — so the command above exits 0 even when the asserts in this file are RED, and
# the assert summary never prints (`docs/FINDINGS.md` FIND-073). Only the `--headless` run
# reports "N asserts held" and returns an exit code worth reading. Its tick count is
# deliberately generous: overshooting the script's own end is free, undershooting truncates the
# run and hides the summary (FIND-032).
#
# ## 🔴 Why there is no `look` in this file any more — read this before adding one back
#
# `src/blades/cut.rs: blade_segment` builds the blade out of `intent.look_dir()`:
# `right = look × Y`, so at yaw 0 the right blade lies on **+X** and at yaw −90 it lies on Z and
# points at nothing. Until 2026-08-19 this file turned the camera with `look -90 -6` **five
# ticks after the trigger, i.e. while the swing was still active** — and that is what made it
# red (`docs/FINDINGS.md` FIND-112). The one-variable control: delete that line and the run goes
# green, leave it and no `Cortex` line is ever logged at any stand-off the blade can reach.
#
# **The camera cannot be turned at all in this run, before OR after the cut**, and that is
# geometry and not laziness:
#
#   * **before** — the blade would leave +X and never reach the nape;
#   * **after** — `docs/images/f034-hitstop.png` is the SAME simulation photographed six ticks
#     later, and a camera that moves between the two frames destroys the one thing the pair
#     proves (the F3 `pos` identical to the digit).
#
# And it was never buying anything: the two PNGs taken **with** the old `look -90 -6` in place
# have no titan in frame either. You cut what you fly past, not what you look at — the cutting
# player is necessarily *beside* the nape, so at the moment of the cut the husk is at 90° to the
# view whichever way the camera is pointed. What the pictures carry is the F3 overlay: the tick,
# the player's position to the digit, `spd 0.0` and `husk#1 Death n/60`. (At yaw 0 the husk does
# get into the right-hand edge of the frame, which the old pair at yaw −90 did not manage.) The
# picture with the husk properly in it is
# `docs/images/f030-solid-husk.png`, out of `scripts/q030-reach.txt`, which turns its camera
# **after** `assert titans == 1` and steps 17 m back to do it.
#
# ## The three ticks this run is read off, and they are not the ones from 2026-08-10
#
# | tick | what happens |
# |---|---|
# | 154 | the blade meets the shoulder — `cut titan 1 Torso at 20.67 m/s`, a graze, `has_grazed` |
# | 157 | the blade meets the nape — `cut titan 1 Cortex at 21.00 m/s`, and the husk dies |
# | 158..164 | the hit stop: 7 ticks, `gear.ron: feel.hit_stop_cortex_s` 0.12 s x 60 |
#
# The cortex crossing sat at tick **154** when this file was written and sits at **157** now —
# one metre further down the same fall, because at 154 the husk is still coming out of his lean
# and the nape has not swung back over his feet yet. `scripts/q030-reach.txt` drifted by the
# same three ticks (its header still says 154) and stayed green through it, because 0.20 m of
# air survives the drift where this file's 0.15 m does not. **`wait 0.12` after the trigger is
# what puts `mark cortex-cut` on the cortex tick and not on the graze.**
#
# ## Why the player FALLS instead of flying
#
# `gear.ron: blades.min_speed_m_s` is 8.0 and `game.ron: player.run_speed_m_s` is 6.0 — a
# running player cannot cut anything, by design ("damage comes out of speed"). The Vector Gear
# reaches 30 m/s and more, but hooking, reeling and boosting cannot be aimed from a script
# accurately enough to pass a 1.10 m sphere. Gravity can: at −20 m/s² a fall of 11.2 m is
# 21 m/s, and it is reproducible to the tick. The player is at y 7.815 on tick 154 and 7.468 on
# 157, and 7.468 again on 160 and on 163 — that is the freeze, measured.
#
# ## Why x = 15.75 and z = 0.8
#
# The husk's body capsule has a radius of `width_fraction × height / 2` = 1.25 m and the player
# capsule 0.35 m, so anything closer than **1.60 m** to his axis is a collision and not a pass.
# 1.75 m leaves 0.15 m of air. The blade is `reach_m` = 1.60 m long and hangs from the hand at
# eye height, so its tip reaches x = 17.35 — 0.15 m inside a cortex sphere of radius 0.55 m
# centred on x = 17.5. **`reach_m` and the body radius are 1.60 m and 1.60 m**: there is no
# margin at all in these numbers, and that is a finding about the RON, not about the cut. The
# cortex also sits `head_m / 2` = 0.55 m **behind** the head's axis (`src/titan/rig.rs:434-440`),
# and z = 0.8 gives up 0.25 m of that offset — the blade still crosses the sphere.
#
# ⚠️ **Do not re-aim this file by centimetres.** `warp 15.70` — the stand-off
# `scripts/q030-reach.txt` flies — does **not** rescue it and never was the fault: swept over
# 15.50 / 15.60 / 15.70 / 15.75 / 15.80, **all five are red** while the mid-swing `look` is in the
# file, and four of the five are green without it. The fifth, 15.50, is a 2.00 m stand-off and
# simply out of the blade's 1.60 m reach — which is the honest lower bound of this pass, and it
# is 15.60..15.80 wide, not one centimetre.
#
# 1.5 s of lead-in before anything happens: under `--offscreen` the render pipelines and the
# block meshes are still coming up in the first second, and a screenshot taken into that is
# evidence of nothing (`scripts/p1-overlay.txt` uses the same 1.5).
wait 1.5
spawn titan husk 17.5 0 0
warp 15.75 18.5 0.8
look 0 0
key F3 0.05
wait 0.90
slash right 0.40
wait 0.12
mark cortex-cut
wait 0.10
assert titans == 1
wait 1.10
assert titans == 0
