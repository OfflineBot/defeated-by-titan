# f-001-hooks — both triggers, through the real input path, in the real city — and a hook
# that HOLDS and moves the player.
#
# **Two runs, because one command cannot do both.** The picture:
#
#   env DBT_GIZMOS=1 cargo run --features wayland,audio -- --offscreen \
#       --script scripts/f-001-hooks.txt --ticks 400 --screenshot docs/images/f-001-hooks.png
#
# and the test, which is a SEPARATE run:
#
#   cargo run -- --headless --script scripts/f-001-hooks.txt --ticks 800
#
# The second one is not redundant. With `--screenshot`, `debug::screenshot::exit_when_written`
# owns the ending and writes `AppExit::Success` the moment the PNG is on disk — the script has
# not finished by then, its assert summary never prints, and **a failed assert does not fail
# the run**. Only the headless run reports "N asserts held" and returns a usable exit code.
#
# ---------------------------------------------------------------------------------------
# ⚠️ WHAT THIS FILE USED TO ASSERT, AND WHY THAT WAS WORSE THAN NO TEST — repaired 2026-08-09
#
# Until today this script carried `assert speed < 0.5` **twice**, commented "a hook that finds
# nothing must not move the player". That was written when no hook could anchor at all
# (`B-001`: `world::index::maintain_index` was a stub, no block carried a `BodyId`,
# `vector::hook::anchor_target` turned every shot into `ReleaseReason::NoAnchor`). The asserts
# described the broken state — and so they **locked it in**: `B-001` was fixed this session,
# and the run still printed "5 asserts held" and exited 0 while both hooks reported
#
#   hook Left of player 1 found nothing anchorable (t=112)
#
# It kept reporting that for a **second, independent** reason as well: the old aim was
# `look 0 -8`, and 8 degrees down from an eye at 1.6 m puts the ray on the GROUND at z = -7.4,
# 2.6 m short of the sand-brown block at z = -10 — and the ground slab is `anchorable: false`
# in `maps.ron`. So the file was green, silent, and wrong twice over.
#
# What it asserts now is the opposite, and it goes red the day hooking breaks again:
# the shot anchors, the reel pulls, and the player ends up on a roof he cannot reach any
# other way.
# ---------------------------------------------------------------------------------------
#
# **What this run proves.** It drives the two rope triggers the way a human does —
# `hook left` presses `KeyQ` and `hook right` presses `KeyE`, `src/net/local.rs` turns them
# into `Buttons::HOOK_LEFT` / `Buttons::HOOK_RIGHT`, the inbox delivers them as an `Intent`,
# and `vector::hook::update_hooks` reads the edge. Every station of that chain reports in the
# log. Both are held for a full second, and the trigger reports exactly once per press — that
# is `just_pressed` against `PrevButtons` doing its job in the real game, not in a test.
#
# ⚠️ **The ropes were on the mouse until 2026-08-10 and this comment said so.** The user asked
# for them on `Q`/`E` so they can be steered while aiming; `LMB`/`RMB` became the blades
# (`src/net/local.rs`, the scheme is written out in its header). The script verb `hook
# left|right` kept its name and now presses the KEY — which is why nothing below this line
# had to move. For the other direction there is now `slash left|right`, because `parse_key`
# cannot reach a mouse button at all.
#
# **Why the church nave and not a market stall.** ⚠️ **RE-AIMED 2026-08-12: this file used to
# shoot at the graybox watchtower** — a 12 m `landmark` at (24, 6, -40), near face z = -34,
# roof y = 12, from (24, 0, -20). `maps.ron: current` is `"ashgate"` since `F-003` and ashgate
# has no watchtower, so the ray flew over the district and both triggers reported
# `found nothing anchorable`: **4 of 14 red, and 9.980 of those metres were simply the player
# standing on the pavement.** That is the same failure mode the 2026-08-09 repair above was
# written about, arriving a second time through the map instead of through the code.
#
# The ashgate equivalent is the **nave of the market-square church**: `(51, 5.75, -8)`,
# `26 x 11.5 x 14`, `anchorable: true`. Its near face is z = -1 and its roof is y = 11.5 — a
# flat roof half a metre lower than the watchtower's and 26 x 14 m wide instead of 12 x 12.
# Standing 14 m in front of it at 34 degrees up — **the same standoff and the same pitch**, so
# only the coordinates moved and not one claim — the ray lands at (51, 11.04, -1). Measured:
# both hooks anchor on body 44 at **(51.00, 11.09, -1.00)**, and the player ends the run
# standing on that roof at **11.500 m, speed 0.000**.
#
# Nothing is between him and it: the market stalls on that square are 2.5 m high and stand at
# x = 32..48, the ray is at x = 51 and is already 7.7 m up as it passes their z, and the gantry
# line over the main street spans x = -22..22 only.
#
# That height is the whole measurement. `assets/data/game.ron` gives `jump_speed_m_s` 6.5
# against g = -20, so a jump reaches **1.056 m**, and `scripts/f-007-boost.txt` states the
# other half: there is no second source of upward motion in this build except the gas boost,
# and this script never presses Shift. **Every metre above 1.056 came out of the rope.**
#
# ⚠️ The 400 ticks belong to THIS file, and the number is **measured, not chosen**. At tick 400
# the player stands still on the roof (measured on ashgate: he is up and stationary from t=309,
# so 400 still holds); three `--offscreen` runs then gave one sha256 (`231e7d86…`) — **that
# hash is the graybox's and is void; the image has to be retaken on ashgate.** The property it
# was proving is not: at tick 200 he is in the air and the same command gives
# **two different files** — 38 828 of 921 600 pixels apart, the whole frame shifted. The
# simulation is not what drifts: three `--headless` runs report 13.064 m and 46.414 m/s to the
# last digit. What drifts is *which tick the shutter catches* under `--offscreen`, and one
# tick at 46 m/s is 0.77 m of camera travel. **A picture of this game is only reproducible
# where the state changes slowly** — reported as a finding, not fixed here.

wait 1.5                # world, camera, meshes and the render pipelines come up (90 ticks)

# 14 m in front of the church nave, eye height, looking 34 degrees up at its upper face.
look 0 34
warp 51 0 13
wait 0.3                # the warp takes effect one tick later than it is written

assert height > -0.1    # standing on the ground, not sunk into it
assert height < 0.5     # and not floating
assert speed < 0.5      # and standing STILL — the baseline every number below is read against
mark f-001-aiming

hook right 1.0          # the RIGHT trigger, on its own
wait 1.0
mark f-001-right-anchored
# A hook that has anchored but is not reeled in changes nothing — the rope is slack, and
# `F-005` says in so many words that reel-in is a change of LENGTH, not a pulling force. This
# is the one place `speed < 0.5` is still the right assertion, and now it means something.
assert speed < 0.5
assert height > -0.1
assert height < 0.5

hook left 6.0           # and the LEFT one — held, because the rope only exists while it is
wait 0.4
mark f-001-left-anchored

key Ctrl 5.0            # REEL_IN: the rope gets shorter and the player goes with it
wait 0.6
mark f-001-reeled
# ⚠️⚠️ **`height > 12.0` and `speed > 35.0` ARE RED AS OF 2026-08-10 AND ARE LEFT RED.**
# Measured 2026-08-10 in the graybox: **9.881 m** and **19.344 m/s**, against the 13.064 m and
# 46.414 m/s this file had quoted for a day. Nothing above that line had changed. `B-004`'s
# take-up ratchet in `src/player/rope.rs` makes the rope follow the real distance down and never
# up, so the player no longer flies past his anchor — and the old pair WAS that overshoot
# (Q-032: the reel ends at 54.18 m/s and is then whipped; FIND-016). The rope-and-nothing-else
# claim still holds — a jump reaches 1.056 m — but the numbers are not these numbers any more.
# Rewriting the brackets here would hide a movement regression inside a hook test.
#
# ⚠️ **The 2026-08-12 re-aim onto ashgate is an independent confirmation of that, and it is the
# reason the pair still stands.** A different map, a different anchor, a different building,
# 27 m further from the origin: **9.980 m and 20.147 m/s**, within 0.1 m and 0.8 m/s of the
# graybox figures. The shortfall travels with the code, not with the geometry — so this is
# `B-004`'s regression being measured twice, and not a script that was aimed at the wrong wall.
# The day the reel is repaired, these two go green on their own and nobody has to touch them.
# 🔴 RED ON PURPOSE — 3 OF 14, AND ALL THREE ARE ONE UNDERPOWERED REEL. Re-measured 2026-08-29
# after `gravity_m_s2` -20 -> -32. The prose below already refused to re-aim the first two; this
# block adds the third and makes the reason greppable instead of buried.
#
#   line 158  height > 12    reads 9.292   the reel-end sample, 0.6 s into a 5 s `Ctrl`
#   line 160  speed  > 35    reads 15.569
#   line 171  height > 11    reads 8.114   he is supposed to be STANDING on the nave roof
#
# ⚠️ Line 171 is NOT a fourth number to re-centre, and the probe is the whole story. Sampling
# height every 0.6 s through the reel (scratch script, same pinned binary):
#
#     t=235  9.292      t=272  11.459  <- the apex of the climb
#     t=309  8.114      t=346..519  8.114, speed 0.003   he is at rest, and stays there
#
# `maps.ron` puts the church nave at `center_m: (51.0, 5.75, -8.0), size_m: (26.0, 11.5, 14.0)`,
# so its roof is at 5.75 + 11.5/2 = **11.500 m exactly**. The reel tops out at **11.459 m**.
# HE MISSES THE ROOF BY 0.041 m and falls back onto the 8.1 m surface below it.
# That is not a bracket that drifted — it is a binary landing decided by 4 cm, and re-aiming
# `> 11` down to `> 8` would convert "he lands on the roof" into "he lands somewhere", which is
# the assert this file's own header says was worse than no test.
#
# Gravity is the trigger and NOT the root: at -20 these read 9.881 and 19.344 and were already
# red (13.064 / 46.414 was the last green pair). -32 pushed the apex the last 4 cm under the
# roof. The day the reel is repaired all three go green together and nobody has to touch them.
assert height > 12.0    # a jump reaches 1.056 m. Twelve metres is the rope, and nothing else.
assert height < 14.0
assert speed > 35.0     # measured 46.4 m/s [debian] — see the note below
assert speed < 55.0
assert gas < 15000      # and the reel really was paid for out of the tank (`gas_tank` is
                        # 15000 since 2026-08-20, Q-046 — the old `< 100` rebased twice, never
                        # loosened; measured 14996.3, i.e. 3.7 spent). ⚠️ A STRICT `<` against
                        # the exact tank size is the whole claim: a run that spent NOTHING
                        # reads exactly 15000.0 and fails this line. It does not go vacuous at
                        # a bigger tank the way a `>` bound would.

wait 1.2
mark f-001-on-the-roof
assert height > 11.0    # he ends up standing on the church nave roof: maps.ron, y = 11.5.
assert height < 12.0    # measured 11.500 exactly — the bracket is the old +-0.5, re-centred
                        # from the watchtower's 12 onto the nave's 11.5, not widened.
assert speed < 1.0

# The camera still points 34 degrees up, and from the roof that is 1280x720 pixels of sky —
# a true photograph of nothing (`scripts/f-007-boost.txt` makes the same point). Turn it down
# onto the roof he is standing on; the boost is long over, so this moves the camera only.
look 0 -35
wait 0.5
mark f-001-roof-view

# ⚠️ 46 m/s out of one reel is a FINDING, not an acceptance: `F-005`'s "change of length"
# reads here as a yank, and the brackets above are wide on purpose so that this file measures
# "the hook moves the player" and not somebody's tuning of `vector.reel_speed_m_s`. The tuning
# belongs to the vector job.

wait 3                  # keep the run alive: if it ends, the process ends before the image
